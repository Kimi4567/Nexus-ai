# D0.3 Study — First-Run Routing & Dashboard Bounce

**Type:** Study / report only. No code, branch, commit, or deploy. No wallet/billing/credits/refunds/subscriptions, analytics/PULSE, publishing/paid/connections/generation, onboarding content, dashboard redesign, or auth behavior changed.
**Method:** Code inspection of `/auth/login`, `/auth/register`, `middleware.ts`, `/dashboard`, `/onboarding`, `/api/workspaces`. Post D0.1 + D0.2.
**Date:** 19 June 2026
**Goal:** Stop a brand-new user from seeing the full dashboard cockpit before onboarding — with the smallest safe change, without breaking auth, existing users, onboarding, or the dashboard.

---

## 1. Executive Recommendation

**Adopt Option A: gate the dashboard's render on the first-run (workspace) check so the cockpit never paints until workspace presence is confirmed.** It is one file (`dashboard/page.tsx`), display-only, changes no auth/routing/onboarding logic, and fully removes the flash. Options B (decide at login) and C (new gate route) are architecturally cleaner but touch auth/middleware/new routes, carry real regression risk for existing/team/verification flows, and are over-engineered for the problem the brief describes. The decision condition (**workspace existence**) and the redirect target (`/onboarding`) stay exactly as they are today — we only stop rendering the cockpit during the brief window before that decision resolves.

---

## 2. Current Route Map

```
REGISTER:  /auth/register → submit → setDone(true) [verify-email screen]
           → (user verifies email via Supabase) → CTA → /auth/login

LOGIN:     /auth/login → signInWithPassword → window.location.href = (?redirect || '/dashboard')
           (login does NOT check workspace; always lands on /dashboard)

MIDDLEWARE: a logged-in user hitting /auth/login|register|forgot-password
           → redirect('/dashboard')   (convenience redirect)

DASHBOARD: /dashboard mounts → authLoading spinner → authed
           → effect: fetch /api/workspaces; if length === 0 → router.push('/onboarding')
           → in parallel: load() fetches stats/campaigns/intelligence; setLoading(false)
           → render gate: if (authLoading || loading) show spinner-in-AppShell, else COCKPIT

ONBOARDING:/onboarding mounts → unauth → /auth/login
           → effect: fetch /api/workspaces; if length > 0 → router.push('/dashboard')
           (its own inverse guard)

WORKSPACE CREATE: /workspace/create → redirect('/onboarding')
```

Every authenticated path funnels through **`/dashboard`** (login redirect, middleware, direct visit). `/dashboard` is the single place the first-run decision is made.

---

## 3. Current Decision Source

- **Who decides onboarding vs dashboard:** the **dashboard page** (and onboarding's own inverse guard). Not login, not register, not a Supabase auth callback (none exists for email; only social callbacks), not middleware (middleware only bounces logged-in users off `/auth/*` to `/dashboard`).
- **Condition used:** **workspace existence** — `GET /api/workspaces` returns `length === 0` → onboarding. It is **not** keyed on BrandProfile, nor on an "onboarding completed" flag. There is **no onboarding-completion flag** in the system; "has a workspace" is the de-facto first-run signal.
- **Workspace query scope:** `GET /api/workspaces` returns `OR[ ownerId = me, members.some(userId = me) ]` — i.e. **owned + member** workspaces. (Important for team/invited users — see risk.)

---

## 4. Bounce / Flash Risk (why it happens)

On `/dashboard` mount, two effects run **in parallel**:
1. the **workspace check** (`fetch /api/workspaces` → redirect if empty), and
2. **`load()`** (3 fetches: stats, campaigns, intelligence brief) which flips `loading=false`.

The render gate is only `if (authLoading || loading) spinner, else cockpit`. The workspace check does **not** gate the render. So it's a **race**:
- If the workspace fetch resolves first (common — it's one light query vs three heavier ones, one of which builds the marketing-intelligence brief) → redirect fires while still in the spinner → onboarding, **no flash**.
- If `load()` resolves first (possible on warm cache / slow workspace query) → `loading=false` → **full cockpit (zero-data) paints for a frame or two** → then the workspace redirect fires → onboarding. **This is the flash.**

So the flash is **intermittent**, not guaranteed — which makes it easy to miss in testing but still a real first-impression risk. Because it's a render-timing race, the fix is a **render gate**, not a logic change.

---

## 5. Option Comparison

### Option A — Gate the dashboard render on the first-run check (RECOMMENDED)
- **What:** add a `firstRunResolved` flag; the workspace effect sets it `true` once the fetch resolves (redirecting if empty); extend the render gate to `if (authLoading || loading || !firstRunResolved) spinner`. Cockpit can't paint until workspace is confirmed **present**.
- **Files touched:** `src/app/dashboard/page.tsx` only.
- **UX benefit:** no cockpit flash for new users; existing users see the same spinner→cockpit they do now.
- **Risk:** **Low** — display-gating only; no auth, routing target, condition, or onboarding change. The single real edge: on a workspace-fetch **error**, the gate must **fail-open** (set `firstRunResolved=true`, proceed to dashboard) so a transient error can't trap the user on a spinner.
- **Complexity:** Minimal (one state + one condition).
- **Impact on existing users:** none (they have a workspace → gate releases immediately after the check).
- **Aligns with first-run trust journey:** Yes — protects the first 3 minutes with the least surface area.

### Option B — Decide at login / auth success
- **What:** after `signInWithPassword`, login fetches `/api/workspaces` and routes to `/onboarding` or `/dashboard` itself.
- **Files touched:** `auth/login/page.tsx` (+ likely a shared helper); does **not** cover direct `/dashboard` visits, the **middleware** `/auth/* → /dashboard` path, or bookmarks — so the dashboard gate would **still** be needed → larger surface.
- **UX benefit:** decision before dashboard mount (cleanest in theory).
- **Risk:** **Higher** — token timing right after sign-in (the session/JWT may not be ready for the immediate `/api/workspaces` call), must re-implement `?redirect` handling, and it **changes auth behavior** (explicitly "do not change yet"). Incomplete without also gating the dashboard.
- **Complexity:** Medium. **Impact on existing users:** medium (every login path reworked). **Aligns:** partially, but over-reaches.

### Option C — Dedicated first-run gate route/component
- **What:** a `<FirstRunGate>` wrapper or a `/start`-style route that checks workspace and forwards.
- **Files touched:** new route/component + wire login redirect + middleware + onboarding guard to it.
- **UX benefit:** centralizes the decision (good long-term).
- **Risk:** **Medium-High** — multiple coordinated changes (login, middleware, onboarding, new route); higher loop risk if any guard disagrees; this is the "new onboarding state system" the brief warns against.
- **Complexity:** High. **Impact on existing users:** medium-high. **Aligns:** yes conceptually, but over-engineered for now.

---

## 6. Recommended Smallest Safe Implementation (for a future PR — not now)

**Option A, dashboard-only render gate:**
1. Add `const [firstRunResolved, setFirstRunResolved] = useState(false)`.
2. In the existing workspace-check effect: in `.then`, if `length === 0` → `router.push('/onboarding')`; **always** `setFirstRunResolved(true)` (in both the empty and non-empty branches). In `.catch`, `setFirstRunResolved(true)` (fail-open).
3. Change the loading gate from `if (authLoading || loading)` to `if (authLoading || loading || !firstRunResolved)` → keep the **existing calm spinner-in-AppShell**.
4. No change to the redirect target, the condition, the onboarding guard, or auth.

Result: a brand-new user sees only the spinner, then onboarding — **never the cockpit**. An existing user's experience is unchanged (the workspace check resolves and the gate releases). Strictly additive, display-only.

---

## 7. Files Likely Touched

- **Only** `src/app/dashboard/page.tsx` (one `useState`, one effect tweak, one render-gate condition).
- **Not touched:** `auth/login`, `auth/register`, `middleware.ts`, `/onboarding`, `/api/workspaces`, or any backend.

---

## 8. Test Plan

1. **New user, no workspace:** log in → see only spinner → land on `/onboarding`; the full dashboard cockpit never paints (verify across warm/cold cache and throttled network, since the bug is timing-dependent).
2. **Existing user, has workspace:** log in → spinner → dashboard renders normally; no added perceptible delay beyond `load()`.
3. **Workspace fetch error (offline/500):** gate **fails open** → user reaches dashboard, not trapped on a spinner.
4. **Team/invited member** (member of a workspace they don't own): `GET /api/workspaces` returns it → routed to dashboard, **not** onboarding.
5. **`?redirect=` param** (e.g. deep link → login): login still honors it; if it points at `/dashboard`, the gate still applies; if elsewhere, behavior unchanged.
6. **Onboarding ↔ dashboard loop:** confirm no loop — the two guards are inverse (`length===0` vs `length>0`) and can't both fire for the same state.
7. **Skipped-onboarding user** (no workspace): returns to onboarding on next dashboard visit (current product behavior — see §9), no flash.
8. **Email-verification path:** register → verify → login → dashboard gate → onboarding (unchanged except no flash).

---

## 9. Risks / Open Questions

- **Fail-open vs fail-closed on workspace-fetch error:** recommend **fail-open** (release to dashboard) so errors never trap the user; the tradeoff is that a (rare) error could still allow a brief cockpit paint. Acceptable and strictly better than a hang. Decision to confirm.
- **"Skipped onboarding" semantics (product question, not a bug):** PX-1 skip does **not** create a workspace, and the dashboard sends any workspace-less user to onboarding. So **skip is a soft defer, not a permanent bypass** — a user who skips keeps returning to onboarding until they complete it (or a workspace is created another way). Option A doesn't change this; if product wants skip to be "remembered," that's a **separate** decision (and would need a real skip/intent flag — out of scope here).
- **Workspace but empty BrandProfile → dashboard (correct):** routing is workspace-only; the dashboard's progressive `getDashboardStage` already handles the empty-brand 'new'/'activating' stages. No special routing needed.
- **Double workspace fetch:** the dashboard and onboarding each fetch `/api/workspaces`; Option A adds no new fetch (reuses the existing effect). Minor existing redundancy, not worsened.
- **Server-side gating (future):** the truly flash-proof approach is a server component / middleware decision before any client render, but that's Option C territory and changes auth/middleware — deliberately deferred.

---

## 10. What NOT to Change

- **Auth behavior** (login/register/verification, `signInWithPassword`, `?redirect`, middleware) — leave as-is.
- **The decision condition** — keep "workspace existence"; do **not** introduce a new onboarding-completion flag or state machine.
- **The redirect target** (`/onboarding`) and **onboarding's inverse guard** — unchanged.
- **Onboarding content, dashboard layout/sections, `getDashboardStage`** — untouched.
- **`/api/workspaces`** (owned+member query) — untouched.
- No new route, no schema, no backend. Keep it a one-file, display-only render gate.

**Bottom line:** the bounce is a client-side render-timing race on the dashboard, decided solely by workspace existence. The smallest safe fix is to hold the dashboard's existing spinner until that one check resolves — one file, no logic change, no auth risk — which guarantees a brand-new user never glimpses the cockpit before onboarding.
